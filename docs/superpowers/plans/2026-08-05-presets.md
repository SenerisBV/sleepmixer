# Plan 3d: presets — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the operator save a mixer configuration under a name and apply it to any song, and make a freshly-opened mixer start from the server's real defaults rather than the schema's flat ones.

**Architecture:** Applying a preset and loading the default config turn out to be the same operation — build a mixer `Config` from a JSON config object plus the schema — so both are one new pure function, `Config.overlay`, tested by `elm-test`. The presets table and its list/create/delete routes already exist; this adds an update route, a default-config route, and a place on the songs row to remember which preset was last used.

**Tech Stack:** Python 3.11 / FastAPI / SQLite · Elm 0.19.2 · pytest · elm-test

**Spec:** `docs/superpowers/specs/2026-08-05-presets-design.md`

## Notes for whoever executes this

**Tasks 1–4 carry their code. Task 5 does not** — it describes the preset bar and gives its pure helpers and tests, but not the view markup, which would be a hundred lines of `Html.div` nobody benefits from reading in a plan. Dispatch Task 5 on a capable model.

**The two riskiest things, in order:**

1. **`Config.overlay` reusing `parse`.** It decodes each incoming JSON value, renders it back to a string, and feeds it through the existing `parse`, so bounds clamping and choice membership are enforced by exactly one code path rather than two that can drift. If that reuse is dropped for a "simpler" direct decode, a preset saved before a bound changed will show a value the server rejects at render time.
2. **What a preset does not carry.** `loop.start_s`, `loop.end_s` and `separation_model`. The first two are seconds into a specific song; the third triggers a multi-minute Demucs run inside the preview lock. Both failures are silent.

```python
    def update_preset(self, preset_id: str, name: str, config: dict) -> dict | None:
        """Rename a preset, replace its config, or both.

        The unique index cannot tell "this name is taken by someone else" from
        "this name is taken by the row I am updating", and the second is the
        common case — saving over a preset without renaming it. So the
        collision is checked explicitly rather than caught, and the two are
        distinguishable to the caller."""
        with self._lock, self._conn:
            row = self._conn.execute(
                "SELECT id FROM presets WHERE id = ?", (preset_id,)).fetchone()
            if row is None:
                return None
            clash = self._conn.execute(
                "SELECT id FROM presets WHERE name = ? AND id != ?",
                (name, preset_id)).fetchone()
            if clash is not None:
                raise ValueError(f"a preset named {name!r} already exists")
            self._conn.execute(
                "UPDATE presets SET name = ?, config = ? WHERE id = ?",
                (name, json.dumps(config), preset_id))
            updated = self._conn.execute(
                "SELECT * FROM presets WHERE id = ?", (preset_id,)).fetchone()
            return _preset_from_row(updated)
```

@router.put("/{preset_id}")
def update_preset(preset_id: str, body: PresetRequest, request: Request) -> dict:
    """Rename a preset, save over it, or both.

    Validated exactly as ``create_preset`` is, and for the same reason: a
    preset that could never render must fail here, not at render time with the
    connection to the offending value long gone."""
    try:
        _validated = MixConfig.from_dict(body.config)  # noqa: F841
    except ValueError as exc:
        raise HTTPException(status_code=400, detail=str(exc))
    try:
        updated = request.app.state.store.update_preset(
            preset_id, body.name, body.config)
    except ValueError as exc:
        raise HTTPException(status_code=409, detail=str(exc))
    if updated is None:
        raise HTTPException(status_code=404, detail="No such preset")
    return updated
```

## Task 2: The server publishes its own defaults, and a song remembers a preset

**Files:**
- Create: `sleepmix/server/api/config.py`
- Modify: `sleepmix/server/app.py`, `sleepmix/server/store.py`, `sleepmix/server/api/songs.py`
- Test: `tests/test_api_config.py`, `tests/test_store.py`, `tests/test_api_songs.py`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces:
  - `GET /api/config/default` → the full default `MixConfig` as a dict, in the shape `MixConfig.from_dict` accepts.
  - `PUT /api/songs/{song_id}/last-preset` — body `{"preset_id": str | null}`; 200 with the updated song, 404 for an unknown song.
  - `songs.last_preset_id` — nullable, exposed on the song row as `last_preset_id`.

**Why the default route exists.** `Config.fromSchema` builds each stem from the schema's flat per-field defaults, and the schema deliberately cannot describe a list, so a mixer opened at defaults differs from `sleepmix render` at defaults on *every* stem — drums enabled against disabled, bass decay enabled against disabled, vocals `linear` to 1600 Hz against `exp` to 2200 Hz. `ui/src/Config.elm`'s own `fromSchema` docstring spells this out and ends "Closing this properly needs the server to publish its default config, not a copy of that list written out in Elm." This is that route.

**Why `last_preset_id` is only a hint.** It is set when a preset is applied or saved, and read to show one line — *"Last used here: Deep erosion"* — with an Apply button. **Nothing applies it automatically.** That was considered and rejected: a preset that re-applies itself means editing it silently changes songs tuned weeks ago. A preset deleted while a song points at it leaves a dangling id; the mixer resolves it against the preset list and shows nothing when it does not resolve.

"""``/api/config`` — the server's own starting point, as values.

Separate from ``/api/schema``, which describes the *shape* of a config: what
fields exist, their types, bounds and choices. That description deliberately
says nothing about list-typed fields, so it cannot express ``MixConfig``'s
curated per-stem list — and a mixer built from the schema alone starts every
stem identical, which is not where the CLI starts. This route closes that by
publishing the values themselves.
"""
from __future__ import annotations

from dataclasses import asdict

from fastapi import APIRouter

from ...config import MixConfig

router = APIRouter(prefix="/api/config", tags=["config"])


@router.get("/default")
def default_config() -> dict:
    return asdict(MixConfig())
```

Register it in `sleepmix/server/app.py` beside the other routers, following exactly how `schema` is included.

`asdict` walks the nested dataclasses and turns `stems` into a list of dicts, which is the shape `from_dict` reads. The round-trip test is what proves that rather than assuming it.

## Task 3: `Config.overlay` and `Config.forPreset`

**Files:**
- Modify: `ui/src/Config.elm`
- Test: `ui/tests/ConfigTest.elm`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces:
  - `overlay : Schema.Schema -> Decode.Value -> Config -> Config`
  - `forPreset : Config -> Encode.Value`

**This task is the whole plan's hinge.** Applying a preset and loading the server's default config are the same operation: take a JSON config object and a base `Config`, and produce a `Config` where every key the JSON carries is replaced and every key it does not is left at the base's value. Since the base is always `fromSchema`'s defaults, "a field the preset does not carry resets to its default" falls out rather than being a special case.

**Reuse `parse` rather than decoding straight to a `Value`.** `parse` already clamps to the schema's bounds and rejects a choice outside the schema's list, and it is what every typed control goes through. Decoding a JSON value, rendering it back through `valueString`, and feeding it to `parse` means bounds live in exactly one place. A preset saved before a bound was tightened then shows a value the mixer will actually accept, rather than one the server rejects at render time.

**`overlay` only touches keys the base already has.** A key in the JSON that the schema does not describe is ignored. That is what lets a preset saved by an older or newer build load without failing.

```elm
{-| Take a config as JSON — a preset, or the server's own defaults — and lay it
over a base config.

Every key the JSON carries replaces the base's; every key it does not carries
the base's through. Callers always pass `fromSchema`'s output as the base, so
"a field this preset does not mention" means "that field's default" rather than
"whatever happened to be on screen". Apply means *make it look like this*, not
*merge this in*: a preset saved before a field existed would otherwise leave
that field holding a value from a recipe the operator believes they replaced,
with nothing on screen saying which control came from where.

Keys the schema does not describe are ignored, which is what lets a preset
written by an older or newer build load rather than fail.

Values go through `parse`, the same function every typed control uses, so the
schema's bounds and choice lists are enforced in exactly one place. A preset
saved before a bound was tightened shows a value the mixer will accept, not one
the server rejects minutes later at render time.
-}
overlay : Schema.Schema -> Decode.Value -> Config -> Config
overlay schema raw base =
    let
        incoming =
            objectOf raw

        incomingStems =
            Dict.get "stems" incoming
                |> Maybe.map stemsByName
                |> Maybe.withDefault Dict.empty
    in
    { top = overlayValues schema Top incoming base.top
    , sections =
        Dict.map
            (\name values ->
                overlayValues schema
                    (InSection name)
                    (Dict.get name incoming |> Maybe.map objectOf |> Maybe.withDefault Dict.empty)
                    values
            )
            base.sections
    , stems = List.indexedMap (overlayStem schema incomingStems) base.stems
    }


objectOf : Decode.Value -> Dict String Decode.Value
objectOf raw =
    Decode.decodeValue (Decode.dict Decode.value) raw
        |> Result.withDefault Dict.empty


stemsByName : Decode.Value -> Dict String (Dict String Decode.Value)
stemsByName raw =
    Decode.decodeValue (Decode.list (Decode.dict Decode.value)) raw
        |> Result.withDefault []
        |> List.filterMap
            (\entry ->
                Dict.get "name" entry
                    |> Maybe.andThen (Decode.decodeValue Decode.string >> Result.toMaybe)
                    |> Maybe.map (\name -> ( name, entry ))
            )
        |> Dict.fromList


overlayStem : Schema.Schema -> Dict String (Dict String Decode.Value) -> Int -> Stem -> Stem
overlayStem schema incoming index stem =
    case Dict.get stem.name incoming of
        Nothing ->
            stem

        Just entry ->
            { stem
                | fields = overlayValues schema (InStem index) entry stem.fields
                , decay =
                    overlayValues schema
                        (InStemDecay index)
                        (Dict.get "decay" entry |> Maybe.map objectOf |> Maybe.withDefault Dict.empty)
                        stem.decay
            }


overlayValues : Schema.Schema -> (String -> Target) -> Dict String Decode.Value -> Values -> Values
overlayValues schema toTarget incoming existing =
    Dict.map
        (\key current ->
            Maybe.withDefault current
                (Maybe.map2 Tuple.pair
                    (Dict.get key incoming)
                    (specAt schema (toTarget key))
                    |> Maybe.andThen (\( raw, spec ) -> fromJson spec raw)
                )
        )
        existing


{-| One JSON value, through the schema's own parser.
-}
fromJson : Schema.Field -> Decode.Value -> Maybe Value
fromJson spec raw =
    let
        text decoder =
            Decode.decodeValue decoder raw |> Result.toMaybe
    in
    (case spec of
        Schema.FloatField _ ->
            Maybe.map String.fromFloat (text Decode.float)

        Schema.IntField _ ->
            Maybe.map String.fromInt (text Decode.int)

        Schema.BoolField _ ->
            Maybe.map
                (\b ->
                    if b then
                        "true"

                    else
                        "false"
                )
                (text Decode.bool)

        Schema.TextField _ ->
            text Decode.string

        Schema.IntChoiceField _ ->
            Maybe.map String.fromInt (text Decode.int)

        Schema.StringChoiceField _ ->
            text Decode.string
    )
        |> Maybe.andThen (parse spec)


{-| The config as a preset should store it.

Two things are removed, and both are silent when they are wrong.

`loop.start_s` and `loop.end_s` are seconds into one particular song. Carried
into a preset they would move another song's loop region to a place chosen for
different audio, and nothing on screen would say why the mix changed.

`separation_model` is not a mix setting at all: changing it nulls the session's
stems, so the next preview runs a real Demucs separation inside the per-song
preview lock — minutes, no progress reporting, on a screen that already
believes itself playable. `Page.Mixer` withholds a control for it by name for
exactly that reason; a preset must not smuggle one in.
-}
forPreset : Config -> Encode.Value
forPreset config =
    encode
        { config
            | top = Dict.remove "separation_model" config.top
            , sections =
                Dict.update "loop"
                    (Maybe.map (Dict.remove "start_s" >> Dict.remove "end_s"))
                    config.sections
        }
```

Check `parse`'s handling of a bool before relying on `"true"` / `"false"` — read it, and if it expects something else, produce what it expects.
