# sleepmix Mixer Implementation Plan (Plan 3b)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Hear the decay arc while you shape it — a mixer with per-stem controls, a scrubber over the arc, and audio that keeps playing while you drag.

**Architecture:** The preview state machine lives in Elm and is therefore testable; `ports/audio.js` fetches, decodes, plays and reports, and makes no decisions. Controls are generated from `/api/schema` decoded into a closed union, so a config field the UI cannot render fails the build. Two small server additions close gaps found by using the thing.

**Tech Stack:** Elm 0.19.2, `elm-test`, Web Audio through one port module, FastAPI.

**Spec:** `docs/superpowers/specs/2026-08-03-sleepmix-ui-design.md`
**Preceded by:** Plans 1, 2a, 2b and 3a — all complete and merged.

## Global Constraints

- **Elm 0.19.2.** `elm/html` and `elm/svg` only. No `elm-ui`, no `elm-css`.
- **No `Debug.toString` or `Debug.log` under `ui/src`** — `elm make --optimize` refuses to build with them. Fine in `ui/tests`.
- **`sleepmix/static/app.js`, `events.js`, `audio.js` and `app.js.sha256` are committed artefacts.** Run `make ui` and commit after any `ui/` change. The hash covers both sources and outputs.
- **Ports carry JSON, never binary.** Elm never touches audio bytes — `audio.js` fetches `/api/preview` itself.
- **The port module makes no decisions.** Coalescing, warming and sequencing all live in Elm, where they can be tested. If you find yourself adding state to `audio.js` beyond the currently-playing source and the in-flight fetch, stop: that logic belongs in Elm.
- Python: ≥3.10, no new runtime dependencies, `fastapi`/`uvicorn`/`starlette` only inside `sleepmix/server/`.
- **Do not automate a browser, use AppleScript, `osascript`, screenshot tools or a browser-driver MCP.** This machine's desktop belongs to the operator; an implementer on Plan 3a tripped a macOS permission dialog they had to dismiss. Verify through the API with `curl`. **This plan is the one where that temptation is strongest, because it produces audio.** You cannot hear it and neither can a screenshot. Verify the bytes and the state machine; the operator listens.
- **Any server you start for checking uses `SLEEPMIX_DATA_DIR=$(mktemp -d)`** so it cannot touch the operator's real library.
- Baseline: 210 Python tests, 60 Elm tests.

## The constraint that shapes this plan

Previews serialize per song, including the cold path — **measured at 117 s cold versus 73 ms warm.** `SessionRegistry.session_for` holds a per-song lock across the whole preview, so a scrubber drag against a cold song queues every request behind the cold render, and each blocked request occupies an AnyIO threadpool thread.

Two consequences, both requirements rather than optimisations:

1. **Never more than one preview request in flight per song.** A drag emits dozens of events; firing one request each would queue dozens of renders. Elm keeps at most one in flight and at most one pending, latest wins.
2. **The scrubber stays disabled until the session is warm.** Entering the mixer fires one preview at progress 0, which is also what `master_gain` calibrates from. Until it returns, the controls are inert and the UI says so.

    def reconcile_orphaned_separations(self) -> int:
        """Reset songs stuck at 'running' to 'pending'. Returns how many.

        The job manager holds its jobs in memory, so a row still marked
        running when the process starts has no job behind it and never will —
        the server was killed or suspended mid-separation. Nothing else clears
        those rows, and a song claiming to separate forever cannot be retried
        from the interface."""
        with self._lock:
            cursor = self._conn.execute(
                "UPDATE songs SET separation_status = 'pending', separation_reason = NULL"
                " WHERE separation_status = 'running'")
            self._conn.commit()
            return cursor.rowcount
```

@router.get("/{song_id}/loop")
def get_loop(
    song_id: str,
    request: Request,
    start_s: float | None = None,
    end_s: float | None = None,
) -> dict:
    """The loop region a render would use, in seconds, plus the tempo estimate.

    Runs on the whole file rather than on separated stems, so it answers before
    separation and needs no warm session. Passing ``start_s``/``end_s`` echoes
    that region back with a tempo — which is what the UI does once you have
    dragged the handles, so the readout stays consistent with what a render
    would actually loop."""
    song = request.app.state.store.get_song(song_id)
    if song is None:
        raise HTTPException(status_code=404, detail="No such song")
    if not os.path.isfile(song["path"]):
        raise HTTPException(
            status_code=404,
            detail=f"Source file unavailable — it has moved or been deleted: {song['path']}")

    buf = load_audio(song["path"])
    config = LoopConfig(start_s=start_s, end_s=end_s)
    point = find_loop(buf, config)
    return {
        "start_s": point.start / buf.sr,
        "end_s": point.end / buf.sr,
        "tempo": point.tempo,
    }
```

```elm
module Preview exposing
    ( Params, State(..)
    , arrived, isPlayable, request, warmed
    )

{-| When to ask the server for a preview, and when not to.

Previews serialize per song — measured at 117 seconds cold and 73 milliseconds
warm — because the server holds a per-song lock across the whole render. A
scrubber drag emits dozens of events, so firing one request each would queue
dozens of renders behind one another and hold a threadpool thread for every
one of them.

So: at most one request in flight, and at most one waiting. A request that
arrives while one is in flight *replaces* whatever was waiting rather than
joining a queue — by the time the server answers, the intermediate positions
are of no interest to anyone.

This lives in Elm rather than in the port module because it is the only part
of the audio path that can be tested. `ports/audio.js` executes what this
decides and decides nothing.
-}

import Json.Encode as Encode


type alias Params =
    { songId : String
    , progress : Float
    , stems : List String
    , config : Encode.Value
    }


{-| The request body `POST /api/preview` actually expects.

The record uses Elm's naming and the API uses Python's, so this cannot be a
`JSON.stringify` of the record — `songId` would arrive as `songId` and the
endpoint would reject it. `stems` is omitted rather than sent empty, because
the server treats a missing `stems` as "every stem the render would process"
while an empty list means "none", which would preview silence.
-}
encode : Params -> Encode.Value
encode params =
    Encode.object
        ([ ( "song_id", Encode.string params.songId )
         , ( "progress", Encode.float params.progress )
         , ( "config", params.config )
         ]
            ++ (if List.isEmpty params.stems then
                    []

                else
                    [ ( "stems", Encode.list Encode.string params.stems ) ]
               )
        )


type State
    = Cold
    | Warming
    | Idle
    | InFlight Params
    | Queued Params Params


{-| Playable once the first preview has returned. Until then the session may
still be building stems and a stretched loop, which is the 117-second path.
-}
isPlayable : State -> Bool
isPlayable state =
    case state of
        Cold ->
            False

        Warming ->
            False

        Idle ->
            True

        InFlight _ ->
            True

        Queued _ _ ->
            True


warmed : State -> State
warmed state =
    case state of
        Warming ->
            Idle

        other ->
            other


{-| Returns the next state and, when there is one, the request to actually send.
-}
request : Params -> State -> ( State, Maybe Params )
request params state =
    case state of
        Cold ->
            ( Cold, Nothing )

        Warming ->
            ( Warming, Nothing )

        Idle ->
            ( InFlight params, Just params )

        InFlight current ->
            ( Queued current params, Nothing )

        Queued current _ ->
            -- Latest wins: the position the user has already moved past is of
            -- no interest by the time the server answers.
            ( Queued current params, Nothing )


{-| Call when a preview returns, whether it succeeded or failed — either way
the slot is free and anything waiting should go now.
-}
arrived : State -> ( State, Maybe Params )
arrived state =
    case state of
        Queued _ pending ->
            ( InFlight pending, Just pending )

        InFlight _ ->
            ( Idle, Nothing )

        other ->
            ( other, Nothing )
```

**The port carries `Preview.encode params`, not the `Params` record.** The
record uses Elm's field names and the endpoint uses Python's; sending the
record directly gives `song_id` missing and a 422 on every request. Declare the
port as `port requestPreview : Encode.Value -> Cmd msg`.

**This module decides nothing.** It holds exactly two pieces of state: the source currently playing, and the fetch currently in flight. Everything about *when* to request lives in `Preview.elm`. If you find yourself adding a queue here, it belongs in Elm.

**Gapless swapping.** A preview is one loop iteration and plays looped. When a new buffer arrives mid-playback, it is scheduled to start at the *next* loop boundary of the current one rather than cutting in — so dragging a decay slider changes the sound at a musical seam instead of a click.

- [ ] **Step 1: Write the port module**

Create `ui/ports/audio.js`:

```javascript
// Web Audio for previews. Fetches, decodes, plays, reports. Decides nothing.
//
// Elm cannot do any of this: ports carry JSON, so audio bytes cannot cross,
// and there is no Web Audio binding. What Elm *does* own is the decision of
// when to ask — see ui/src/Preview.elm — because that is the part that can be
// tested. This module holds two pieces of state, the playing source and the
// in-flight fetch, and nothing else. A queue here would be a bug.
//
// Swapping is scheduled at the next loop boundary rather than immediate, so
// changing a decay setting mid-playback lands on a musical seam instead of a
// click.

export function wire(app) {
  let context = null;
  let playing = null; // { source, startedAt, duration }
  let inFlight = null; // AbortController

  const ensureContext = () => {
    if (context === null) {
      context = new (window.AudioContext || window.webkitAudioContext)();
    }
    // Browsers start the context suspended until a user gesture; every
    // request follows a click or a drag, so resuming here is safe.
    if (context.state === "suspended") context.resume();
    return context;
  };

  const nextBoundary = (ctx) => {
    if (playing === null) return ctx.currentTime;
    const elapsed = ctx.currentTime - playing.startedAt;
    const cycles = Math.ceil(elapsed / playing.duration);
    return playing.startedAt + cycles * playing.duration;
  };

  const play = (ctx, buffer) => {
    const source = ctx.createBufferSource();
    source.buffer = buffer;
    source.loop = true;
    source.connect(ctx.destination);

    const at = nextBoundary(ctx);
    source.start(at);
    if (playing !== null) playing.source.stop(at);
    playing = { source, startedAt: at, duration: buffer.duration };
  };

  const stop = () => {
    if (playing !== null) {
      try {
        playing.source.stop();
      } catch (err) {
        // Already stopped; harmless.
      }
      playing = null;
    }
  };

  if (app.ports && app.ports.requestPreview) {
    app.ports.requestPreview.subscribe(async (params) => {
      if (inFlight !== null) inFlight.abort();
      inFlight = new AbortController();
      const controller = inFlight;

      try {
        const response = await fetch("/api/preview", {
          method: "POST",
          headers: { "content-type": "application/json" },
          body: JSON.stringify(params),
          signal: controller.signal,
        });
        if (!response.ok) {
          const detail = await response.text();
          throw new Error(`server answered ${response.status}: ${detail}`);
        }
        const bytes = await response.arrayBuffer();
        const ctx = ensureContext();
        const buffer = await ctx.decodeAudioData(bytes);
        if (controller !== inFlight) return; // superseded while decoding
        play(ctx, buffer);
        app.ports.previewReady.send({ durationS: buffer.duration });
      } catch (err) {
        if (err.name === "AbortError") return; // Elm already moved on
        app.ports.previewFailed.send(String(err.message || err));
      } finally {
        if (controller === inFlight) inFlight = null;
      }
    });
  }

  if (app.ports && app.ports.stopPreview) {
    app.ports.stopPreview.subscribe(() => {
      if (inFlight !== null) {
        inFlight.abort();
        inFlight = null;
      }
      stop();
    });
  }
}
```

Note that an aborted fetch reports nothing back to Elm. That is deliberate and it is the one place this module's dumbness has a sharp edge: Elm must not be left waiting for a reply that will never come. `Preview.request` only ever emits a new request from `Idle`, and `audio.js` only aborts when a new request arrives — so the abort is always immediately followed by a fetch whose outcome *is* reported. **Verify that invariant holds when you wire Task 5**, and say so in your report.

### Task 5: `Schema.elm` — controls from the server's own description

**Files:**
- Create: `ui/src/Schema.elm`, `ui/tests/SchemaTest.elm`
- Modify: `ui/src/Request.elm`

**Interfaces:**
- Produces:
  - `Field = FloatField Spec | IntField Spec | BoolField BoolSpec | ChoiceField ChoiceSpec`
  - `decoder : Decoder Schema`, `Request.schema`

**Why this is the point of choosing Elm.** `/api/schema` describes every config field — bounds, units, labels, choices — so the UI generates its controls instead of hard-coding them. Decode it into a *closed* union and a field type the UI cannot render fails the decode loudly, exactly as `Api.elm`'s statuses do. In a dynamically typed frontend the same change renders nothing and says nothing.

**The real shape, fetched from the running server rather than guessed.** These
are verbatim fragments of `GET /api/schema`; build the decoder against them:

```json
"speed":       {"type":"float","default":0.7,"label":"Speed","help":"Playback speed as a fraction of the original. 0.7 = 70% speed.","min":0.05,"max":1.0,"step":0.01,"unit":"×"}
"sample_rate": {"type":"int","default":44100,"label":"Sample rate","help":null,"unit":"Hz","choices":[22050,44100,48000]}
"enabled":     {"type":"bool","default":true,"label":"Enabled","help":null}
"curve":       {"type":"str","default":"linear","label":"Curve","help":"linear · exp …","choices":["linear","exp","log"]}
"start_s":     {"type":"float","default":null,"label":"Loop start","help":"Leave empty to auto-detect a beat-aligned loop.","min":0.0,"unit":"s"}
```

Every `(type, has-choices)` combination the server actually emits:
`(bool,no) (float,no) (int,no) (int,yes) (str,no) (str,yes)` — six, not four.
Note in particular that `default` can be `null` (`start_s`), that `help`,
`min`, `max`, `step` and `unit` are all optional, and that a plain `str` with
no choices exists (`separation_model`) and needs a text input rather than a
select.

- [ ] **Step 1: Write the failing test**

Create `ui/tests/SchemaTest.elm` using the fragments above **as string
literals**, so the test pins the server's real output rather than an imagined
shape. Cover: each of the six combinations decoding to its intended variant;
`start_s` decoding with a `Nothing` default and no `max`; a field whose `type`
is unrecognised **failing the decode**; and a whole section round-tripping.

- [ ] **Step 2: Run to verify it fails, then implement**

Create `ui/src/Schema.elm`:

```elm
module Schema exposing (Field(..), Schema, Section, decoder, fieldLabel)

{-| The server's own description of its config, decoded into something the
compiler can check.

Controls are generated from this rather than hand-written, so a new config
parameter appears in the interface without a frontend change. The union is
closed on purpose: a field type this application cannot render fails the
decode loudly instead of rendering nothing. That is most of the reason the
project chose Elm.
-}

import Dict exposing (Dict)
import Json.Decode as Decode exposing (Decoder)


type alias NumberSpec =
    { label : String
    , help : Maybe String
    , default : Maybe Float
    , min : Maybe Float
    , max : Maybe Float
    , step : Maybe Float
    , unit : Maybe String
    }


type alias BoolSpec =
    { label : String, help : Maybe String, default : Bool }


type alias TextSpec =
    { label : String, help : Maybe String, default : Maybe String }


type alias ChoiceSpec a =
    { label : String, help : Maybe String, default : Maybe a, choices : List a }


type Field
    = FloatField NumberSpec
    | IntField NumberSpec
    | BoolField BoolSpec
    | TextField TextSpec
    | IntChoiceField (ChoiceSpec Int)
    | StringChoiceField (ChoiceSpec String)


type alias Section =
    { fields : Dict String Field }


type alias Schema =
    { fields : Dict String Field, sections : Dict String Section }


fieldLabel : Field -> String
fieldLabel field =
    case field of
        FloatField spec ->
            spec.label

        IntField spec ->
            spec.label

        BoolField spec ->
            spec.label

        TextField spec ->
            spec.label

        IntChoiceField spec ->
            spec.label

        StringChoiceField spec ->
            spec.label


decoder : Decoder Schema
decoder =
    Decode.map2 Schema
        (Decode.field "fields" (Decode.dict field))
        (Decode.field "sections" (Decode.dict section))


section : Decoder Section
section =
    Decode.map Section (Decode.field "fields" (Decode.dict field))


{-| Dispatch on the type *and* on whether choices are present: the server emits
`int` and `str` both with and without them, and a select and a slider are not
interchangeable.
-}
field : Decoder Field
field =
    Decode.map2 Tuple.pair
        (Decode.field "type" Decode.string)
        (Decode.maybe (Decode.field "choices" Decode.value))
        |> Decode.andThen
            (\( kind, choices ) ->
                case ( kind, choices ) of
                    ( "float", _ ) ->
                        Decode.map FloatField numberSpec

                    ( "int", Nothing ) ->
                        Decode.map IntField numberSpec

                    ( "int", Just _ ) ->
                        Decode.map IntChoiceField (choiceSpec Decode.int)

                    ( "bool", _ ) ->
                        Decode.map BoolField boolSpec

                    ( "str", Nothing ) ->
                        Decode.map TextField textSpec

                    ( "str", Just _ ) ->
                        Decode.map StringChoiceField (choiceSpec Decode.string)

                    ( other, _ ) ->
                        Decode.fail ("unknown config field type: " ++ other)
            )


numberSpec : Decoder NumberSpec
numberSpec =
    Decode.map7 NumberSpec
        (Decode.field "label" Decode.string)
        (Decode.field "help" (Decode.nullable Decode.string))
        (Decode.field "default" (Decode.nullable Decode.float))
        (Decode.maybe (Decode.field "min" Decode.float))
        (Decode.maybe (Decode.field "max" Decode.float))
        (Decode.maybe (Decode.field "step" Decode.float))
        (Decode.maybe (Decode.field "unit" Decode.string))


boolSpec : Decoder BoolSpec
boolSpec =
    Decode.map3 BoolSpec
        (Decode.field "label" Decode.string)
        (Decode.field "help" (Decode.nullable Decode.string))
        (Decode.field "default" Decode.bool)


textSpec : Decoder TextSpec
textSpec =
    Decode.map3 TextSpec
        (Decode.field "label" Decode.string)
        (Decode.field "help" (Decode.nullable Decode.string))
        (Decode.field "default" (Decode.nullable Decode.string))


choiceSpec : Decoder a -> Decoder (ChoiceSpec a)
choiceSpec value =
    Decode.map4 ChoiceSpec
        (Decode.field "label" Decode.string)
        (Decode.field "help" (Decode.nullable Decode.string))
        (Decode.field "default" (Decode.nullable value))
        (Decode.field "choices" (Decode.list value))
```

`numberSpec` uses `Decode.nullable` for `default` (the server sends `null` for
`start_s`) but `Decode.maybe (Decode.field …)` for `min`/`max`/`step`/`unit`
(the server omits those keys entirely). Those are different situations and the
two decoders are not interchangeable — `nullable` fails on a missing key.

Add `Request.schema` following the shape of the existing request functions.
